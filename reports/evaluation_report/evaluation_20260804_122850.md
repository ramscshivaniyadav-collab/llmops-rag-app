## ✅ PASS - test_case_1

<details><summary><b>View Test Case Data</b></summary>

- **Input:** How do ML systems and LLM apps differ in determinism, dynamic cost, and input-output tracking?
- **Actual Output:** Determinism
- ML systems: deterministic — same input (row) yields the same output every time (e.g., a regression model returns 10 for that input, a classifier always returns the same label). Outputs are simple and well-defined (binary labels or bounded continuous values).
- LLM apps: probabilistic — the same prompt can produce different outputs on different calls. Outputs are free-form text (words, sentences, paragraphs) and can vary in wording, length and content, so you cannot rely on a single fixed response.

Dynamic cost
- ML systems: costs are predictable per unit of data/compute (e.g., 100 rows consistently incur the same compute/cost).
- LLM apps: costs are dynamic and hard to fix because both input and output token lengths vary and affect pricing; retrieved context (from retrievers/vector DB) and workflow steps also change compute and cost. You can set max output length but actual usage (and hence cost) still fluctuates.

Input–output tracking (workflow and evaluation)
- ML systems: prediction is usually a single deterministic step — you rarely must track an end-to-end workflow for each prediction; standard, fixed formulas (accuracy, precision, recall, MSE, R²) make evaluation straightforward.
- LLM apps: prediction is a multi-step workflow (prompting, retrieval, context assembly, model call, post-processing). You must manage the relationship between input and output, track all moving parts (retriever, vector DB, prompts), and evaluate outputs by intent/quality rather than simple label matching. Evaluation is tricky and essential (e.g., hallucination risk can produce fabricated facts with real-world consequences), so thorough end-to-end testing and monitoring are required.
- **Expected Output:** ML systems are generally deterministic: the same input row gives the same output every time, with fixed compute/cost for that input size.  

LLM apps are probabilistic and dynamic: the same input can produce different outputs, and both cost and compute vary because input length, output length, and retrieved context all change.  

Also, ML prediction usually has a simple input-to-output flow, while LLM apps often require tracking the full journey from input through retrieval, prompting, and output.

</details>

## ✅ PASS - test_case_2

<details><summary><b>View Test Case Data</b></summary>

- **Input:** How can a generator hallucinate despite correct retrieval, and what causes it?
- **Actual Output:** Short answer: a generator can still hallucinate even if the retriever returned the correct document. Causes from the given context:

- Document-order / position bias: the generator tends to rely more on higher-ranked (earlier) retrieved documents, so a correct fact in a lower-ranked doc can be ignored.
- System-prompt / instruction weighting: prompts that tell the generator to prioritize certain docs (or earlier docs) can make it pick incorrect facts from higher-priority docs.
- Wrong synthesis / mixing facts: the generator can combine facts from different retrieved documents (or take a fact from the wrong doc) and produce an incorrect answer (e.g., mixing a Python-course duration into the ML answer).
- No re-ranking: if you don’t re-rank retrieved docs, the correct doc may be present but deprioritized and effectively unused by the generator.
- Probabilistic (non-deterministic) behavior: LLM outputs vary for the same input and may sometimes produce incorrect outputs even with the same context.
- Instruction/format mismatch or generation failures: the model may not follow the expected output format or rubric, producing an output that’s functionally wrong even though context was correct.
- Chunking / context-building differences: how documents are chunked or assembled into context can change what the generator sees and cause errors.

These are the causes discussed in the context.
- **Expected Output:** A generator can hallucinate even when retrieval is correct by ignoring the retrieved context and producing an answer from its own assumptions or from unrelated parts of the context. This happens because the retriever may fetch the right documents, but the generator can still misread them, over-prioritize certain text, or add unsupported facts.

</details>

<details><summary><b>View Test Case Data</b></summary>

- **Input:** How do LLM evals differ from software tests in fixed vs. flexible output and multi-metric quality?
- **Actual Output:** - Fixed vs. flexible output
  - Software tests: outputs are deterministic and fixed — same input → single expected output (e.g., 2+3 must be 5). Tests are pass/fail against that expected value.
  - LLM evals: outputs are probabilistic and flexible — the same input can produce many different but valid answers. There is a large grey area because multiple different responses can all be “right,” so you cannot rely on a single expected string to decide pass/fail.

- Single-metric correctness vs. multi-metric quality
  - Software tests: you mostly measure correctness (is the output exactly what you specified).
  - LLM evals: you must evaluate many dimensions beyond correctness, for example:
    - Relevance (did it answer the asked question or something else — e.g., gave definition of underfitting when asked about overfitting),
    - Completeness,
    - Grounding/source attribution (especially for RAG systems: is the answer based on the retrieved documents?),
    - Safety and toxicity,
    - Style/clarity (matches desired explanation style),
    - Latency and cost (response time, token usage), etc.
  - Because of these multiple criteria, evaluation is not a single metric exercise.

- Practical implications (from the context)
  - LLM evals must be systematic, repeatable, and based on clear criteria: create datasets covering edge cases, define rubrics for each quality dimension, and run the same tests across versions to compare performance.
  - LLM evaluation is a complete testing setup (datasets, criteria, tooling, offline/online procedures), not just computing one metric.
- **Expected Output:** LLM evals are harder than software tests because:

- **Software tests** usually check **fixed, deterministic output** — one input should produce one expected answer, so it’s mostly **pass/fail**.
- **LLM evals** deal with **flexible, probabilistic output** — the same prompt can produce different but still valid answers.

Also, software testing mostly checks **correctness only**, while LLM evals need **multi-metric quality checks** like:
- correctness
- relevance
- completeness
- groundedness
- safety

So, unlike software tests, LLM evals are not just about “right or wrong”; they evaluate whether the answer is good across multiple dimensions.
