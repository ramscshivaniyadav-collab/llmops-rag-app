## ✅ PASS - test_case_1

<details><summary><b>View Test Case Data</b></summary>

- **Input:** How do ML systems and LLM apps differ in determinism, dynamic cost, and input-output tracking?
- **Actual Output:** Determinism
- ML systems are deterministic: the same input row (with same features and model/hyperparameters) gives the same output every time (e.g., a logistic regression row always outputs 0 or 1). Evaluation uses fixed formulas (accuracy, precision, MSE).
- LLM apps are probabilistic: the same prompt can produce different outputs on different runs. Outputs are variable in wording and length, so you cannot rely on a single fixed answer.

Dynamic cost
- ML systems have predictable cost per workload: e.g., 100 rows may always consume the same compute/cost (fixed x units).
- LLM apps have dynamic cost: both input length and output length vary, so API cost and compute change per request. Retrieved context (retriever, vector DB) and workflow steps also affect compute, making cost hard to fix and estimate; you must plan headroom and limits.

Input–output tracking
- ML systems: prediction is immediate and simple; there is usually no multi-step runtime workflow to trace, and labels/ground truth are fixed and well defined.
- LLM apps: there is a workflow (retrieval, prompt assembly, model call, postprocessing) with moving parts (retriever, vector DB). Because outputs are probabilistic and text can be valid in many forms, you must manage and track the relationship between inputs and outputs end-to-end (logging, provenance, evaluation of intents), otherwise evaluation and debugging become difficult.
- **Expected Output:** ML systems are generally deterministic: the same input row gives the same output every time, with fixed compute/cost for that input size.  

LLM apps are probabilistic and dynamic: the same input can produce different outputs, and both cost and compute vary because input length, output length, and retrieved context all change.  

Also, ML prediction usually has a simple input-to-output flow, while LLM apps often require tracking the full journey from input through retrieval, prompting, and output.

## ✅ PASS - test_case_2

<details><summary><b>View Test Case Data</b></summary>

- **Input:** How can a generator hallucinate despite correct retrieval, and what causes it?
- **Actual Output:** - Ordering / attention bias: the generator tends to rely more on the higher-ranked (earlier) documents. If the correct fact is lower in the K results, the model can ignore it and pick a conflicting fact from an earlier doc.

- Prompt/system-prompt bias: the system prompt can instruct the generator to prioritize certain docs or to weigh context in a particular order, causing it to prefer wrong facts.

- Fact blending / context mixing: the model can merge facts from multiple documents and produce a composite but incorrect answer (e.g., take "Python = 6 weeks" from one doc and apply it to "ML").

- Model probabilism / non-determinism: LLMs are probabilistic; even with the same context they may produce different outputs and sometimes invent details.

- Insufficient grounding constraints: if the generator is not explicitly constrained to only use retrieved context (or not given a strict rubric), it can fall back to internal knowledge or invent details.

- Output-format/expectation mismatch: if you expect a specific format or specificity and the model isn’t guided well, it can output a different (and wrong) form of the answer.

- Lack of re-ranking / poor context ordering: without re-ranking or a way to surface the most relevant doc first, correct evidence can be present but low-priority and effectively ignored.

- Ambiguous or underspecified user query: if the question is vague, the generator may fill gaps with plausible but incorrect facts.

These are the typical causes when retrieval is correct but the generator still hallucinates.
- **Expected Output:** A generator can hallucinate even when retrieval is correct by ignoring the retrieved context and producing an answer from its own assumptions or from unrelated parts of the context. This happens because the retriever may fetch the right documents, but the generator can still misread them, over-prioritize certain text, or add unsupported facts.

</details>

<details><summary><b>View Test Case Data</b></summary>

- **Input:** How do LLM evals differ from software tests in fixed vs. flexible output and multi-metric quality?
- **Actual Output:** - Fixed vs. flexible output
  - Software tests: outputs are fixed and deterministic. One input → one expected output (e.g., 2+3 must be 5). Tests are binary (pass/fail).
  - LLM evals: outputs are probabilistic and flexible. The same input can produce many different — but valid — answers (different wording, length, emphasis). Because there is no single correct string, you cannot use simple equality checks; you need rubrics, multiple references, or similarity-based evaluation.

- Single-metric correctness vs. multi-metric quality
  - Software tests: you mostly check correctness only (is the answer right or wrong).
  - LLM evals: you must measure many dimensions, not just correctness. Examples: relevance, completeness, groundedness (is the answer based on your data in a RAG system), safety (no abusive or harmful output), latency, cost (token usage), style/clarity, and provenance. A real example: for a CampusX RAG chatbot you’d check correctness, simple explanation style, whether the answer came from course content, safety, response time, etc.

Because of these two differences, LLM evaluation needs systematic, repeatable test setups and clear evaluation criteria rather than simple pass/fail test cases.
- **Expected Output:** LLM evals are harder than software tests because:

- **Software tests** usually check **fixed, deterministic output** — one input should produce one expected answer, so it’s mostly **pass/fail**.
- **LLM evals** deal with **flexible, probabilistic output** — the same prompt can produce different but still valid answers.

Also, software testing mostly checks **correctness only**, while LLM evals need **multi-metric quality checks** like:
- correctness
- relevance
- completeness
- groundedness
- safety

So, unlike software tests, LLM evals are not just about “right or wrong”; they evaluate whether the answer is good across multiple dimensions.
